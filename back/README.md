# Бэкенд («Краски детства»)

FastAPI + SQLAlchemy + Alembic. REST API для сайта и админ-панель.

## Структура

| Файл / папка | Назначение |
|---|---|
| `main.py` | создание приложения: роутеры, `/uploads`, логирование запросов, раздача сборки фронта, `/api/health` |
| `database.py` | подключение БД: `DATABASE_URL` из окружения (Postgres), без него — SQLite `back/database.db` |
| `models.py` | таблицы: `managers`, `pictures`, `donations`, `logs` |
| `schemas.py` | Pydantic-схемы валидации запросов/ответов |
| `auth.py` | bcrypt-хеши паролей, JWT-токены, проверка текущего пользователя |
| `admin_panel.py` | админка `/admin`: статистика, загрузка картинок, пожертвования, лог |
| `routers/` | API-роутеры: `auth_router`, `pictures`, `donations`, `logs` |
| `alembic/`, `alembic.ini` | миграции БД (файлы миграций — в `alembic/versions/`) |
| `uploads/` | загруженные картинки, доступны по `/uploads/<файл>` |
| `requirements.txt` | зависимости Python |
| `Dockerfile` | образ бэкенда для Docker |

## Локальный запуск

```bash
cd back
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

alembic upgrade head            # создать/обновить таблицы
uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

Адреса после запуска:
- Swagger (документация API): http://localhost:8000/docs
- Админка: http://localhost:8000/admin
  - логин/пароль первого администратора берутся из `ADMIN_LOGIN` / `ADMIN_PASSWORD`;
    если их нет, генерируется временный пароль и печатается в логе запуска;
  - пароли в репозиторий не коммитим — только `.env` (он в .gitignore).

## Оплата (HIH-9)

Раздел `/admin/settings`: чекбокс «Оплата включена» (по умолчанию выкл) и учётные данные
шлюза Сбербанка. Base URL — env `SBER_BASE_URL`; прямой протокол передаёт JSON и не
использует `merchantLogin` в `register.do`. Пока оплата выключена,
чекаут работает по старой схеме (заглушка paid). При включённой оплате `POST /api/orders`
регистрирует платёж и отдаёт `payment_url`, покупатель уходит в шлюз, а статус заказа
меняется только после `getOrderStatus.do` на маршрутах `/payment/return` и `/payment/fail`.

## 8. Диагностика оплаты через Сбербанк (тест работает, бой — нет)

Где смотреть, ничего не воспроизводя вслепую:

1. **`/admin/settings`** — вверху показан активный контур (`PROD`/`TEST`) с полным
   endpoint, режим проверки TLS, а у каждого поля — **источник** значения:
   «БД (админка)» или «env SBER_…». Ниже — предупреждения, если конфигурация
   противоречива. Кнопка **«Проверить доступ к шлюзу»** дёргает `getOrderStatus.do`
   со служебным номером: платёж не создаётся, а по ответу видно, где именно поломка —
   TLS, сеть, учётные данные или всё в порядке.
2. **`/admin/logs`** — строки `SBER register.do → HTTP 200 (…мс)` и, с этой версии,
   ещё и `SBER … → СБОЙ …`. В `request` пишутся `userName`, `merchantLogin`,
   `terminal`, `endpoint`, `verify_ssl` и источник учётки; **пароль и ключ не
   пишутся никогда** (маскируются по полям `password|secret|token|authorization|key`).

Типичные причины «на тесте работает, на бою пароль не подходит» — по убыванию
вероятности:

| # | Проверить | Как выглядит |
|---|---|---|
| 1 | **Корневой сертификат боевого шлюза.** На тесте проверка TLS отключена (`SBER_VERIFY_SSL=false`), поэтому та же проблема на бою проявляется впервые | в логе `TLS-рукопожатие не прошло … certificate verify failed / unable to get local issuer certificate` |
| 2 | **Боевая учётка не та.** Пароль из тестового мерчанта на `securepay.sberbank.ru` не работает в принципе — боевые данные выдаёт инженер Сбера | `errorCode` с текстом про пароль/аутентификацию, при этом TLS и сеть в порядке |
| 3 | **Значения в БД перекрывают env.** Приоритет: БД → env → дефолт. Если на бой скопировали базу с тестовыми ключами, env их не переопределит | в админке у поля источник «БД (админка)», а предупреждение говорит «в БД и в env разные значения» |
| 4 | **Пароль со спецсимволами.** Docker compose раскрывает `${...}` и внутри значений `.env`, поэтому пароль с `$` доезжает обрезанным | в логе userName корректный, а пароль «не подходит»; предупреждение «значение содержит «$»» |
| 5 | **Другие имена переменных.** Код читает `SBER_BASE_URL`/`SBER_USER_NAME`, но понимает и алиасы `SBER_API_URL`/`SBER_USERNAME` (с предупреждением) | предупреждение «userName читается из SBER_USERNAME» |

Про сертификат — важная деталь, о которой часто забывают: **httpx доверяет не
системному хранилищу, а bundle пакета `certifi`** (`create_ssl_context` в httpx
0.28 использует `certifi.where()`, если не заданы `SSL_CERT_FILE`/`SSL_CERT_DIR`).
Значит просто положить `.crt` в образ и выполнить `update-ca-certificates`
недостаточно. Рабочих варианта два:

```bash
# A) смонтированный сертификат (без пересборки образа) — deploy/certs/ проброшен
#    в контейнер как /etc/sber-certs
SBER_CA_BUNDLE=/etc/sber-certs/nuc-root.crt

# B) сертификат вшит в образ из deploy/certs/*.crt — тогда переключаем httpx на системное хранилище
SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt
```

Подробнее — `deploy/certs/README.md`. Отключать `SBER_VERIFY_SSL` на боевом контуре
нельзя: это открывает подмену шлюза.

Чего в текущей реализации **нет**, чтобы не искать несуществующее:

- шифрования секретов в таблице `settings` (в том числе AES-256-GCM) — значения
  лежат в открытом виде, защищены только доступом к БД и маскированием в UI и логах;
- проверки подписи ответов шлюза — `sber_key_id`/`sber_key` сохраняются, но никуда
  не отправляются и не проверяются; статус заказа решается только серверным
  `getOrderStatus.do`;
- отправки `terminal` в запросах шлюза — поле хранится и показывается, но имя
  параметра в `register.do` не подтверждено.

## База данных

- Без переменных окружения — SQLite, файл `back/database.db`.
- С `DATABASE_URL` (например `postgresql://postgres:postgres@db:5432/hand_in_hand`) — Postgres; так работает в Docker.
- Изменения схемы — только миграциями:

```bash
alembic revision --autogenerate -m "описание изменения"
alembic upgrade head
```

## Основные эндпоинты API

| Метод | Адрес | Описание | Доступ |
|---|---|---|---|
| POST | `/api/auth/login` | вход, выдаёт JWT | все |
| GET | `/api/pictures` | список рисунков | все |
| POST | `/api/pictures/upload` | загрузка картинки | админ |
| PATCH | `/api/pictures/{id}` | изменение рисунка | админ |
| POST | `/api/donations` | создать пожертвование | все |
| GET | `/api/donations` | список пожертвований | админ |
| PATCH | `/api/donations/{id}/status` | смена статуса пожертвования | админ |
| GET | `/api/logs` | лог запросов | админ |
| GET | `/api/health` | проверка здоровья сервиса | все |

Полный актуальный список — в Swagger: `/docs`.

## Запуск в Docker (весь стек)

Из корня репозитория:

```bash
bash deploy/deploy.sh   # Postgres → миграции → фронтенд → API
bash deploy/stop.sh     # остановка
```

Порты: API — 8000, фронтенд — 3000, Postgres — 5432.
